Architecture decision guide / 20 September 2026

Teams Phone ≠ ACS-free

Teams Phone changes the telephony identity. TPE still uses ACS for call control and audio.

Keep that integration, replace it with Graph or a SIP gateway, or move the conversation into a managed product. These are different workstreams, not interchangeable provider settings.

Microsoft's integration models: Unify = ACS, Extend = Graph, Connect = certified SBC + Direct Routing.

Baseline ACS owns call control and duplex audio. License checklist

02 Teams Phone via ACS / TPE

Proposed Accelerator integration design based on public TPE documentation. License checklist

Reuse the ACS bridge; add Teams identity. TPE connects a licensed resource account and service number to ACS Call Automation. The design shown here aims to retain the Python runtime, callbacks, and media protocol; that reuse must be implemented and validated. TPE architecture · GA scope.

Next proof: Teams admin + app owner. Provision the RA, assign server access, and exercise inbound/outbound calls and the intended human-handoff route against the public prerequisites.

Known limit: Teams → third-party agent → external-number transfer/conference is documented as failing. Exact scenario.

Teams/TPE architecture, call flows & public prerequisites

Reuse

ACS Call Automation, Event Grid/callbacks, duplex media, both engines, hangup, YAML agents/tools/scenarios, Redis/Cosmos.

Add

Teams RA, service number, licensing, app identity, RA-to-ACS association, server access assignment, carrier route; SBC/DNS/certificates when using Direct Routing.

Replace, not remove

Replace the ACS-purchased source-number assumption with Teams RA identity. Do not remove ACS control or media.

03 ACS-independent Graph calling bot

Proposed New calling bot, media host, and bridge. License checklist

Keep Python behind a Windows/.NET media service. Graph controls calls, including documented PSTN scenarios; its REST API does not stream PCM. Graph v1.0 calling · Media requirements.

Next proof: identity + media-platform owners. Obtain the relevant Graph consent, validate Azure Windows hosting/support, then prototype a duplex bridge to the existing engine.

Support gate: Graph REST is v1.0; the separate real-time media platform page still says developer preview. This is not a Linux-only drop-in.

Graph architecture, call flows & media-host requirements

Reuse

Python AI engines, YAML definitions/tools, and storage behind an explicit new bridge. Reuse is a design goal, not current channel compatibility.

Add

Entra app/calling bot, application instance, Graph consent, Azure Windows/.NET media hosts, per-call affinity, callbacks, and a custom duplex/control bridge.

Remove from this path

ACS Call Automation, ACS Event Grid integration, ACS media framing, and ACS-number identity. Audit email/SMS separately before claiming complete ACS removal.

Graph supports PSTN origination, inbound, and transfer scenarios. Follow the application-instance/number prerequisites, rather than assuming every identity can call any destination. The transfer API notes a same-tenant Teams scope and PSTN transfer only for application instances. Bot number management · Answer · Transfer and asynchronous response.

REST v1.0 is not the media platform's release label. The application-hosted media article still calls the real-time media platform developer preview. It requires the Microsoft.Graph.Communications.Calls.Media .NET library, production Windows Server hosting in Azure (not Azure Web App), publicly reachable per-instance IP/port mapping, and call affinity. Calls remain pinned to their media host. The SDK must be current or no more than three months old. Confirm the operational and support boundary before committing. Exact media-host constraints.

04 SIP gateway + Teams Direct Routing

Proposed Gateway vendor and interface not selected. License checklist

Keep Python behind a programmable SIP/contact-center gateway. The gateway owns call control and duplex audio; a certified SBC supplies Teams connectivity. Connect model · Direct Routing prerequisites.

Next proof: telephony vendor + app owner. Confirm simultaneous audio receive/injection, auth/codecs, and blind/consultative transfer in the selected topology before building the channel bridge.

Not sufficient: a certified SBC alone is not an AI media API, and does not certify the whole voice-agent solution.

SIP architecture, call flows & vendor transfer contract

Reuse

Python/Linux hosting, AI engines and business definitions, tools, and state behind a purpose-built channel bridge.

Add

Selected gateway/control service, confirmed duplex API, certified SBC, carrier/Teams routing, DNS/certificates/networking, monitoring, and vendor operations.

Remove from this path

ACS control, callbacks/Event Grid, ACS framing, and ACS number dependency. The gateway replaces these responsibilities; they do not disappear.

No invented endpoint: this guide deliberately does not name a generic wss:// SIP media URL. Transport, authentication, codecs, pacing, interruption, concurrency, and commercial rights remain vendor-dependent and unconfirmed.

Transfer direction matters. Microsoft's Direct Routing article describes the Teams SIP proxy either handling a transfer locally with a new INVITE, or sending REFER to the SBC, which handles a new INVITE using the provided context. SBC NOTIFY support is required; SBC REFER handling is required for the documented media-bypass transfer case. This is not a guarantee that an arbitrary bot-originated REFER into Teams will work. Validate REFER-TO/REFERRED-BY, Replaces behavior, and blind/consultative flows with the SBC/gateway vendor. Official SIP transfer contract.

A certified SBC establishes the Direct Routing device boundary, not certification of the entire voice-agent solution. Agree which party owns carrier incidents, Teams routing, gateway media, and the AI runtime. Contact-center solution certification.

05 Managed Teams Phone Agent / Copilot Studio

Preview Replace the conversational runtime, not just the phone provider. Teams Phone Agent licenses · Copilot Studio licenses

Move the conversation into a managed product. The native setup lists no custom ACS resource or PCM bridge to this accelerator; Microsoft's internal stack is undisclosed. Teams Phone Agent · Direct-dial Copilot Studio.

Next proof: Teams/Power Platform admins + agent owner. Confirm preview eligibility and test one representative conversation, tool call, and supported human transfer.

Fit gate: the Copilot Teams channel is basic-voice only, not real-time, with classic orchestration and tenant enablement. Do not assume Cascade/VoiceLive or outbound-automation parity. Channel limits.

Managed architecture, call flows & preview boundaries

Carry forward

Business requirements, reviewed prompts, knowledge, and allowed tools as migration inputs, not drop-in YAML/runtime reuse.

Add

Product eligibility, tenant/channel enablement, licensed RA/number configuration, managed agent configuration, governance, and product-specific testing.

Replace

This application's telephony integration and conversational runtime. External business services may be connected only through supported product mechanisms.

Basic voice is not real-time channel parity. The linked Copilot Studio Teams channel supports basic voice agents only; real-time voice agents are explicitly unsupported. It calls for classic orchestration (not generative orchestration), tenant enablement by Microsoft, and Copilot Studio tenant/user licensing. Do not use Dynamics 365 real-time voice-agent documentation as proof of Teams channel support. Teams channel prerequisites and limitations · Separate Dynamics 365 real-time offering.

Teams Phone Agent remains Frontier Public Preview; direct-dial Copilot Studio is also preview. Native RA transfer, tools, and recording features have their own boundaries. These are not GA replacements with automatic parity for Cascade, VoiceLive, arbitrary outbound calls, or SIP automation. Product status and limitations.

TPE: server access is not client-user consent

The documented server flow associates the RA with the ACS resource, then the ACS resource owner creates a Teams access assignment for the tenant/RA with principalType: "teamsResourceAccount". The separate Calling SDK client-user flow uses TeamsExtension.ManageCalls, admin consent, and permitted client IDs; do not present that as the server-only Call Automation grant. Optional Graph RA discovery uses a beta endpoint and is not a production prerequisite when administrators already provide the RA object ID. Server vs client assignments · Provisioning and discovery.

Human handoff: acceptance is not completion

Every path needs an observed outcome and a failure fallback. A YAML agent handoff changes the AI persona, not the telephone call.

Destination, transfer, outcome & recovery checklist
1

Resolve

Teams identity vs E.164 number; tenant scope, destination allowlist, caller consent, and identity policy.

2

Attempt

Blind vs consultative; hold/media ownership, new call legs, timeout, and correlation ID.

3

Observe

Accepted vs completed; asynchronous callback/notification, busy, no answer, rejection, and disconnect.

4

Recover

Retain caller or offer a designed fallback; avoid duplicate transfers; release only the correct media/legs.

Context is a separate data path. A summary, authentication state, transcript, and CRM reference do not automatically travel with a phone call. Use an authorized integration, scoped identifiers, and explicit retention/access policy. SIP headers or TPE context headers are not a universal human-desktop context protocol. ACS exit workstreams

These are proposed delivery checkpoints, not assigned tasks or a release schedule. Reuse the current business logic; replace and prove each ACS-specific boundary.

Voice migration is not complete ACS removal. If your application also uses ACS Email or SMS, migrate those dependencies separately. Teams Phone telephony does not replace transactional email or programmable messaging.

Voice control + media
Choose a voice path: Graph media bot or SIP gateway. App/media owners replace create/answer/transfer, callbacks, framing, identity, and cleanup. Runtime extension boundary.
Call-lifecycle proof
App + telephony owners: prove inbound/outbound, duplex audio, barge-in, DTMF, human handoff, failure recovery, and hangup; recording/announcements where required.
Email + SMS
Choose replacements where needed: migrate tools, templates, credentials, delivery tracking, and consent/compliance independently of the voice path.
Commercial + admin approval
Tenant + service owners: confirm licenses/consent, carrier and solution support, preview limits, and applicable public lifecycle guidance before a production commitment.
Final dependency audit
Release owner: verify no remaining ACS consumers before removing resources, secrets, numbers, roles, or deployment configuration. No removal is performed by this guide.
